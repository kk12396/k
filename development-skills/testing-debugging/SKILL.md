# 系统化修 Bug Skill

## 适用范围

出现任何报错、闪退、页面异常、数据错误、卡顿、构建失败、安装失败、接口失败、迁移失败、跨端不一致或“已经改过但仍然报错”时，必须先执行本 Skill，再提出或实施修复。

问题看起来很小、用户催得急、已经尝试过修复或“感觉原因很明显”时，更不能跳过流程。

## 四条硬规则

1. **没有完成根因调查，不得直接改代码。** 看到报错位置不等于找到根因，必须追溯错误数据、状态或配置最早从哪里产生。
2. **一次只验证一个明确假设。** 不得同时改多个文件、依赖、配置和逻辑后再碰运气测试，否则无法判断哪项有效。
3. **没有新鲜验证证据，不得宣称修好。** 代码已修改、编译器没提示、页面能打开一次、AI/子任务说成功，都不能证明问题已解决。
4. **同一问题连续三次修复失败后必须停止盲修。** 不得继续叠加第4个补丁；先重新检查架构、共享状态、依赖、版本和前提假设，并向用户报告卡点后再决定是否重构。

# 阶段0：保护现场

修复旧项目前先保留当前可回退状态：

- 读取现有源码、配置、数据库迁移、日志和最近改动，不从头重做。
- 记录当前版本、环境、依赖和可复现步骤；必要时保存原文件或 Git diff。
- 禁止通过清库、重装、删除数据、关闭校验、吞异常或返回假成功“修复”问题。
- 用户数据、旧功能和现有安装升级能力必须保留。

# 阶段1：根因调查

## 1. 完整读取错误

必须读取完整错误信息、警告、堆栈、文件路径、行号、错误码、前置日志和后续异常，不得只看最后一行或截图标题。

优先收集：

- Android：完整 Java/Kotlin native 堆栈、logcat、Android版本、机型、ABI、权限、安装来源、是否覆盖升级。
- Web/PHP：PHP版本、MySQL版本、Web服务器、完整错误日志、请求参数、响应、SQL错误、目录权限和部署路径。
- KSWEB：共享存储路径、实际写入测试、`flock/LOCK_EX/rename` 行为、PHP扩展和日志文件。
- 双/三端：客户端请求、API网关、服务端、数据库和文件存储每一层的输入、输出、状态码及时间线。

敏感日志必须脱敏，不得打印密码、令牌、数据库凭据或完整私密内容。

## 2. 建立稳定复现

记录：入口、操作步骤、输入、账号状态、设备/环境、网络、文件大小、预期结果和实际结果。

- 能稳定复现：继续调查。
- 偶发问题：增加时间戳、线程、生命周期、请求ID和状态日志，重复运行收集模式。
- 无法复现：继续补证据，不得凭猜测提交修复。

## 3. 检查最近变化

对比最近可用版本与当前版本：代码 diff、依赖、Gradle/PHP/MySQL版本、权限、配置、数据库迁移、签名、混淆/加固、服务器和系统环境。

## 4. 多组件边界取证

系统经过多个层级时，在每个边界记录：

- 进入了什么数据和状态；
- 输出了什么数据和状态；
- 配置、环境变量、身份和版本是否正确传递；
- 失败最先出现在哪一层。

先通过一次完整运行确定“在哪一层坏掉”，再调查该层，禁止同时修改所有端。

# 阶段2：反向追踪与模式对比

## 1. 从症状向上追踪

按以下链路持续追问，直到找到最早触发点：

`报错位置 → 直接原因 → 谁调用它 → 参数/状态从哪里来 → 最初错误输入或状态在哪里产生`

修复源头，不只修复报错处。找到源头后，可在关键边界增加必要校验和防御，但不能用多层兜底掩盖根因。

详细方法见 `ROOT_CAUSE_TRACING.md`。

## 2. 找到同项目中的正常样例

寻找同类功能中能够正常工作的代码、页面、接口或旧版本，逐项比较：参数、生命周期、线程、权限、路径、配置、依赖版本、数据库字段、返回结构和调用顺序。

所有差异都先记录，不得主观认定“这个肯定无关”。

## 3. 阅读完整参考实现

使用框架、插件、SDK或已有模式时，必须完整读取相关实现和官方文档，不能只复制局部代码或凭印象改写。

# 阶段3：假设与最小实验

每轮必须留下假设记录：

```text
假设编号：H1
根因假设：我认为X是根因
证据：因为日志/对比显示Y
最小实验：只改变Z或增加某项诊断
预期：若假设成立，应出现A；否则出现B
实际结果：
结论：确认 / 否定 / 证据不足
```

规则：

- 每次只改变一个变量。
- 优先增加诊断或构造最小复现，不直接进行大范围重构。
- 实验失败后撤销无效改动，形成新的假设；不得在旧补丁上继续堆补丁。
- 不理解某段行为时必须明确说明并继续取证，不得装作确定。

# 阶段4：实施根因修复

1. 先建立能失败的回归测试、测试脚本或稳定复现步骤，证明修复前确实失败。
2. 只实施解决已确认根因的最小修改，不夹带“顺手重构”、UI改版或无关优化。
3. 保留旧数据、接口、配置和升级兼容；数据库修改使用幂等增量迁移。
4. 对源头完成修复后，在输入、边界或危险操作处增加必要校验，防止同类错误再次进入系统。
5. 修复记录必须写明：现象、根因、触发条件、影响范围、修改位置和回归范围。

# 阶段5：完成前验证门禁

在说“已修复”“可以了”“测试通过”前，必须执行 `VERIFICATION_GATE.md`。

至少验证：

- 原始复现步骤现在通过；
- 回归测试在修复代码存在时通过；条件允许时撤销修复后应重新失败，再恢复修复后通过；
- 完整构建命令退出码为0，而不是只通过语法检查；
- Android APK完成签名验证、安装、启动和核心流程；涉及旧应用时完成同签名覆盖升级；
- Web完成对应PHP/MySQL环境的安装、登录、核心请求和迁移测试；旧版记录KSWEB实际结果或未验证项；
- 关联功能、边界输入、异常路径、权限拒绝、断网、重试和旧功能未回归失败；
- 测试输出中失败数为0，或明确列出仍失败的项目。

任何未运行的验证必须写“未验证”，不能用“应该、理论上、看起来、估计”代替证据。

# 连续失败控制

- 第1次假设失败：回到阶段1，利用新证据重新定位。
- 第2次假设失败：重新比较正常样例、环境和数据流，检查是否遗漏共享状态或版本差异。
- 第3次修复仍失败：立即停止继续补丁，输出 `BUG_SESSION_REPORT.md` 格式的阶段报告，并检查架构是否错误、模块是否强耦合、状态源是否重复、旧迁移/旧数据是否冲突。
- 未与用户说明架构问题和重构影响前，不得开始第4轮大改。

# 针对“AI一直修不好”的强制行为

用户表示“还是报错”“又错了”“修了很多次”“别再猜”或提供新的同类堆栈时：

1. 立即停止沿用上一次未经证实的猜测。
2. 汇总已经尝试过的修改及每次实际结果，避免重复同一方案。
3. 回滚或隔离无效补丁，重新读取最新完整代码和最新错误，而不是基于旧版本继续回答。
4. 建立证据表和调用链，先指出错误最早出现在哪一层。
5. 若缺文件、日志或运行环境才能确认，精确列出所需材料；同时继续完成不依赖这些材料的静态检查。
6. 不得只发零散代码片段让用户反复手动拼接；能修改完整项目时，应交付完整修复文件或可检查的阶段包。

# 禁止表述与禁止做法

- “大概率是……直接这样改就行”但没有日志或实验支持。
- 一次提交多个可能修复，再让用户碰运气。
- 只修改报错行，不追踪错误数据来源。
- 通过注释功能、删除校验、关闭混淆、清库、重装或吞异常掩盖问题。
- 仅看到编译通过就声称业务 Bug 已修复。
- 把旧日志、旧源码或子任务的“成功”当作当前版本验证。
- 连续失败后仍回复“再试这个版本”而不总结证据和改变方法。

# 输出要求

每轮调试至少简要输出：

```text
现象：
稳定复现：是/否
已收集证据：
当前根因假设：
本轮只验证的变量：
实验结果：
确认的根因：未确认/内容
实施的修复：
验证命令与结果：
仍未验证：
下一步：
```

最终报告使用 `BUG_SESSION_REPORT.md`，不得省略失败尝试和未验证项。
