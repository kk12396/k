# 根因反向追踪指南

本文件用于错误出现在深层调用、堆栈很长、错误参数来源不明或多个组件相互调用的情况。

## 核心原则

错误出现的位置通常只是症状。必须沿调用链向上追踪，直到找到最初错误输入、状态、配置或生命周期事件产生的位置，再从源头修复。

## 标准追踪链

```text
表面症状
→ 直接触发错误的代码
→ 调用这段代码的上层
→ 传入的错误参数或状态
→ 参数/状态的来源
→ 最早产生错误值或错误时序的位置
```

每向上一层都回答：

1. 这里实际收到的值和状态是什么？
2. 谁传入了这个值？
3. 这个值在上一层为何会变成这样？
4. 它在哪个时间点首次偏离正常值？
5. 同类正常流程中的值有什么不同？

## 无法直接追踪时的取证

在危险操作发生前增加临时诊断，而不是只在失败后打印一句错误：

- 请求ID、时间戳、线程或协程；
- 调用者和完整堆栈；
- 输入值的类型、长度、是否为空和业务状态；
- 当前目录、文件路径、权限和剩余空间；
- Android Activity/Fragment/Service 生命周期；
- API请求路径、状态码和服务端对应日志ID；
- 数据库迁移版本、字段是否存在、事务状态；
- 配置来源和最终生效值。

敏感字段只记录是否存在、长度或哈希摘要，不记录密码、令牌和数据库密钥。

## 多层系统追踪

对于 `客户端 → API → 业务服务 → 数据库/文件`：

1. 客户端记录发送前的业务状态和请求ID。
2. API入口记录收到的请求ID、身份和参数校验结果。
3. 业务层记录状态转换和调用结果。
4. 数据层记录查询/迁移结果和错误编号。
5. 用同一请求ID串联时间线，找出第一处与预期不一致的层。

对于 `源码 → 构建 → 加固 → 签名 → 安装`：

1. 记录每一步输入产物的SHA-256、包名、版本和签名状态。
2. 确认哪一步首次改变了Manifest、资源、DEX、JNI或证书。
3. 最终签名后不得再执行会改写APK内容的步骤。

## 修复源头后的防御

找到并修复源头后，可在关键边界增加：

- 非空、范围、格式和业务状态校验；
- 明确错误码和可定位日志；
- 非法目录、非法URL或危险操作拒绝；
- 数据库版本和字段存在性检查；
- 生命周期取消和重复回调保护。

防御层用于阻止错误再次扩散，不能替代源头修复。

## 完成标准

只有同时满足以下条件，才算完成根因追踪：

- 能画出或写出完整调用/数据链；
- 能指出错误最早在哪一层产生；
- 能解释为何只在特定设备、版本、数据或操作顺序下发生；
- 修复位置位于源头或正确边界，而不只是崩溃行；
- 有回归测试证明同类错误不会再次进入系统。

参考基础：`obra/superpowers` 的 Systematic Debugging 与 Root Cause Tracing，按本项目环境重新整理。
