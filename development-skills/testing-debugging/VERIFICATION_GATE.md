# 修复完成前验证门禁

## 硬规则

没有本轮新执行的验证证据，不得使用“已修复、已解决、通过、完成、没问题、可以使用”等结论。

## 声明完成前的五步门禁

1. **确定证据**：什么命令、操作或测试可以直接证明该结论？
2. **重新执行**：在当前最新代码和当前产物上完整运行，不能引用旧结果。
3. **完整读取**：查看完整输出、退出码、失败数量、警告和实际产物。
4. **对照结论**：证据是否真的支持“已修复”，还是只支持“编译通过”或“某一步通过”？
5. **如实报告**：证据支持才宣布完成；不支持则报告实际状态和剩余问题。

## 不同结论所需证据

| 结论 | 必须具备 | 不能替代 |
|---|---|---|
| Bug已修复 | 原始复现步骤通过，且关联回归无失败 | 代码已修改、肉眼看起来正确 |
| 测试通过 | 完整测试命令退出码0、失败数0 | 上一次测试、只跑一个模块 |
| 构建成功 | 干净构建命令退出码0，产物真实存在 | 语法检查、IDE没有红线 |
| APK可用 | 签名验证、安装、启动和核心流程通过 | APK文件存在、仅编译成功 |
| 可覆盖升级 | 使用同签名从旧版本覆盖安装且数据保留 | 新装成功 |
| Web可部署 | 对应PHP/MySQL环境安装、登录、核心功能和迁移通过 | 本地静态页面能打开 |
| 数据库升级安全 | 旧数据升级、重复迁移、失败恢复通过 | 新库安装成功 |
| 加固后可用 | 加固后重新签名、安装、启动、网络、JNI/模型/插件和核心功能通过 | 加固工具显示成功 |
| 双/三端一致 | 功能矩阵逐项联调通过 | 各端分别能启动 |

## 回归测试红绿验证

条件允许时，回归测试应证明它真的覆盖本次Bug：

1. 修复存在时运行，测试通过；
2. 临时撤销关键修复，测试应失败；
3. 恢复修复，再次运行，测试通过。

若无法执行红绿验证，应说明原因，不得把“写了测试”直接等同于“测试有效”。

## Android最低验证

- `apksigner verify` 或同等签名验证通过；
- APK可直接安装并首次启动；
- 关键页面、权限、文件、网络和返回操作正常；
- 旧应用升级时验证同签名覆盖安装和数据保留；
- 加固后检查反射、JNI、OCR/模型、插件和资源没有被误删；
- 记录包名、版本、证书SHA-256和APK SHA-256。

## Web最低验证

- 所选PHP版本语法检查；
- 所选MySQL版本安装或迁移测试；
- 后台登录、会话、CSRF和权限；
- HTTP/HTTPS两种配置按需求工作；
- 旧版记录KSWEB写入、配置保存、上传和迁移的实测或未验证状态；
- 错误日志不泄露敏感信息。

## 禁止用语

未完成验证时不得写：

- “应该可以了”
- “理论上已解决”
- “肯定没问题”
- “代码没报错，所以修好了”
- “工具显示成功，所以能用”

应改为：

```text
已完成代码修改；已验证：……；仍未验证：……；当前不能确认：……
```
