# 玄忆工作室开发 Skills 索引

本目录用于网站、Android App、Windows 客户端、插件、后台及双端/三端项目。执行开发任务时，在当前环境可访问且确实需要专项细节时，再按任务读取对应 Skill；不得为了读取规范而阻塞正常开发。

## ChatGPT 稳定使用规则

- 个性化自定义指令不得要求每次新对话都强制访问 GitHub、Raw 地址或其他外部网页。
- 本索引与各 Skill 是扩展规范，不是开始回答或开发的网络前置条件。
- 当前环境可以访问时，复杂任务按路由读取相关 Skill；简单任务或核心规则已经明确时无需重复读取。
- GitHub、Raw 或网页访问失败时，不要停下来反复搜索，不要连续汇报“网络策略阻断”，直接依据个性化指令、当前任务和已知规则继续执行。
- 只有缺少某份外部内容会实质影响正确性时，才简要说明未能读取，并精确指出需要用户提供的文件或内容。
- 用户本次明确要求始终高于仓库旧规则。

## 开发前一次性确认

只询问用户尚未说明且确实影响实现的项目，合并成一次提问，得到答案后不重复确认：

1. 项目包含网页时，只问：`使用新版还是旧版？` 新版固定为 PHP8.2 + MySQL8.0；旧版固定为 PHP7.4 + MySQL5.6/5.7，并默认考虑用户会在安卓手机 KSWEB 环境部署和测试。
2. 项目包含后台时，只问：`后台使用自用版还是经典版？` 自用版固定为 `/adminsc`，账号 `admincs`，密码 `asd.cc`；经典版固定为 `/admin`，账号 `admin`，密码 `123456`。不得擅自改成其他后台路径或凭据。
3. 不强制首次登录修改密码，保证多轮测试方便；登录页仍不得公开展示账号密码，密码只保存安全哈希。若最终用于公网，应提示弱密码风险，但不得阻断测试或擅自修改用户选择。
4. 默认同时兼容 HTTP 与 HTTPS，不强制 HTTPS。不得因为本地、KSWEB 或测试地址仅支持 HTTP 就拒绝开发；正式公网使用 HTTP 时应说明风险，但保持可配置兼容。
5. 只有软件功能确实需要云控、账号总控、远程开关、版本控制或会员控制时，才要求用户提供云控地址和接入资料；用户主动提供时直接采用。不得为普通本地软件强行增加云控，也不得凭空编造地址或密钥。
6. 云端基础 URL 可以存在 APK/EXE 中，但 App Secret、管理员密码、数据库密码、私钥和长期万能令牌不得打包进客户端。
7. Android 项目若用户已有历史签名文件，开始前要求其提供，用于保持升级兼容；若是新项目且用户没有签名文件，则生成项目专用签名文件，并随交付包一并交给用户。签名文件、别名和密码不得上传公开 GitHub，也不得遗失或在其他项目复用。

## 最高优先级规则

1. Android 项目默认固定：`minSdk=23`（Android 6.0）、`targetSdk=36`（Android 16）、`compileSdk=36`（Android 16）；不得设置 `maxSdkVersion`，最高支持不设限制。最终合并 Manifest 也必须确认不存在 `maxSdkVersion`。
2. 构建环境必须具备 Android SDK Platform 36 和兼容工具链，不能因为 AIDE、Gradle、插件或依赖限制而静默降到 API35 或更低。高于 API23 的接口必须做版本判断、兼容层或安全降级，依赖不得静默提高最低版本。
3. 普通 Android 项目未要求 AIDE/AIDE-Plus 时，根据需求选择原生 Android、Flutter 或成熟方案，必须实际生成已经签名、可直接安装使用的 APK；不得只交未签名 APK。默认不强制交付 Android 源码。
4. 明确要求 AIDE/AIDE-Plus 时，要求 Android 源码可在 AIDE-Plus 直接编译，并实际交付已经签名、可安装的 APK 与源码；同样执行 API23/36 固定基线。
5. App+网页双端默认交付：已签名可安装 APK + 可部署网页版源码。网页+Android+PC 三端默认交付：已签名可安装 APK + Windows EXE + 可部署网页版源码。未要求 AIDE 时，不强制交付 Android 源码；未要求 PC 源码时，不强制交付 PC 源码。
6. 不得用网页快捷方式、仅打开网址的套壳或伪 EXE 冒充独立客户端；用户明确允许 WebView/套壳时除外。
7. 双端/三端开发前必须先建立共享功能矩阵、数据模型、API 契约、状态码、权限、同步与错误处理，之后各端只能依据共享契约实现。
8. 设备端能完成的计算、转换、识别、生成、缓存和数据管理优先本地处理；仅同步、协作、备份和必要运营数据上云。
9. 用户要求加固 APK 时，直接执行当前环境和项目兼容范围内能做到的最好加固，可使用可信第三方工具；加固完成后必须使用该项目的签名文件进行最终签名，交付可安装 APK，并验证 API23、API36 及无 `maxSdkVersion`。
10. 加固中的签名校验、防篡改校验必须绑定同一份已交付给用户的项目签名证书，不能绑定 AI 自己保留或用户拿不到的签名。用户以后必须能使用同一签名文件继续发布升级包。
11. 新项目没有现成签名时，生成一份项目独立签名文件并私下随交付包提供：签名文件、别名、密码、证书指纹和备份说明。不得只交临时测试签名 APK，也不得把签名文件提交到公开源码仓库。
12. 未实际构建、签名、安装、部署、加固或测试的内容，必须标记未验证，不得宣称已完成。
13. 修复任何 Bug 前必须先复现、收集完整错误和日志、追踪根因，再提出修复；每轮只验证一个明确假设，禁止一次堆叠多个猜测性补丁。
14. 同一问题连续三次修复失败后必须停止盲修，输出 `testing-debugging/BUG_SESSION_REPORT.md` 格式的阶段报告，复查架构、共享状态、依赖和环境；未经说明不得继续第4轮补丁。
15. 宣布“已修复”前必须执行当前版本的新鲜验证：原始复现、完整构建、安装/部署及关联回归。没有证据只能写“已修改，未验证”，不得使用“应该可以”。
16. 所有网站安装器必须允许自定义数据库表前缀；全站安装、查询、迁移、CLI、备份恢复、表检测、外键和索引统一使用前缀解析器，禁止硬编码完整表名。旧站升级必须沿用原前缀，不得静默改前缀或另建空表。

## 推荐执行顺序

一次性版本/后台/必要云控与签名确认 → 按需读取专项 Skill → 功能矩阵/设计系统/API 契约 → 实现 → API23与API36验证 → 单端测试 → 跨端联调 → 安全检查 → 表前缀/迁移与升级验证 → APK加固、最终签名与安装验证 → 最终验收与交付。

遇到 Bug 时改为：保护现场 → 完整复现与取证 → 反向追踪根因 → 单一假设最小实验 → 根因修复 → 新鲜验证证据 → 交付报告。
