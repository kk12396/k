# Android App Skill

## 云控只在需要时确认

只有软件确实需要账号总控、会员、远程开关、版本控制、设备绑定、到期控制、公告或其他云控能力时，才要求用户提供云控地址及接入资料；用户主动提供时直接采用。普通本地工具不得强行增加云控。

需要云控但用户未提供时，开发前询问：云控基础地址、App Key/应用标识、认证方式、环境和必要接口资料。不得凭空编造云控地址、App Secret 或可用凭据。

云控基础 URL 本身通常不是秘密，可打包进 APK，也可设计为配置项。App Secret、管理员密码、数据库密码、私钥和长期万能令牌必须只保留在服务端。客户端通过用户登录、设备注册、短期令牌和服务端权限校验访问云控。

默认兼容 HTTP 与 HTTPS，不强制 HTTPS。本地、局域网、临时测试和无证书云控地址应可使用；公网 HTTP 需提示窃听和篡改风险，但不得因此拒绝实现。网络安全配置只对白名单域名放开必要的明文流量，避免全局无条件放开。

## 技术路线

### 未要求 AIDE/AIDE-Plus

根据产品需求、性能、设备覆盖、现有项目和维护成本，选择原生 Android、Flutter 或成熟可靠方案。

默认交付要求：

- 必须实际生成已经签名、可直接安装使用的 APK。
- 不得把未签名 APK、仅能等待用户二次签名的 APK 或临时占位包作为主要交付物。
- 默认不强制交付 Android 源码；用户明确要求源码时再交付。
- 不得只交工程目录、伪 APK、网页快捷方式或无法安装的占位文件。
- 实际执行构建、签名和安装验证，并记录构建方式、最低 Android 版本、目标版本、包名、版本号、证书指纹和 APK 路径。

### 明确要求 AIDE/AIDE-Plus

- 优先原生 Android/Java、Groovy Gradle、少依赖和本地静态资源。
- 工程必须可在 AIDE-Plus 直接打开和编译，交付已经签名、可安装的 APK 与完整 Android 源码。
- 复杂 Kotlin、JNI、ONNX、OpenCV、PaddleOCR 等产物应提前构建为兼容 AAR/JAR/so 或静态模型，再作为工程输入。
- 不得声称 AIDE 可编译却只在 Android Studio 验证。

## 项目签名规则

Android 同一应用后续升级必须继续使用与首个发布版本一致的签名证书，因此签名文件必须由用户最终持有。

### 用户已有签名文件

- 修改旧项目或发布已有应用时，优先要求用户提供原签名文件、别名和密码。
- 使用原签名完成 release、加固后的最终签名和升级安装验证。
- 不得换用临时签名，否则会导致覆盖升级失败或签名校验失效。

### 新项目且用户没有签名文件

- 生成该项目独立的 release 签名文件，不得复用其他用户或其他项目的签名。
- 使用这份签名完成最终 APK 签名，使交付 APK 可直接安装使用。
- 将签名文件、别名、密码、证书 SHA-256 指纹、有效期和备份说明放入单独私密交付包一并给用户。
- 签名文件和密码不得提交公开 GitHub、公开源码包、日志或截图；不得由 AI 独占、扣留或仅交付证书而不交付私钥文件。
- 明确提醒用户妥善备份：遗失签名文件后通常无法继续覆盖升级已安装应用。

## 正式 APK 默认安全

所有正式 release APK 默认执行：

- `debuggable=false`，移除测试入口、演示账号、调试证书和敏感日志。
- 启用与项目兼容的代码压缩、资源压缩、优化和混淆，补齐反射、JNI、序列化、路由和插件保留规则。
- 最小化导出 Activity、Service、Receiver、Provider，并为必要导出组件添加权限或严格输入校验。
- 检查备份、截图、剪贴板、WebView、深链、文件 URI、本地数据库和崩溃日志泄密。
- 本地令牌使用 Android Keystore 支持的安全存储，不把长期秘密写入 strings.xml、assets、BuildConfig 或明文数据库。
- 默认兼容 HTTP/HTTPS；仅对必要域名放开明文流量，不强制用户必须部署 HTTPS。

## 用户说“加固 APK”时

不再询问加固等级，直接做当前环境、技术栈和项目兼容范围内能实现的最好加固，可使用可信第三方工具。

加固流程至少包括：

1. 生成干净 release APK，关闭调试和测试配置。
2. 执行代码与资源压缩、优化、混淆，强化保留规则并检查反射/JNI/模型/插件兼容。
3. 清除敏感字符串、日志、测试地址、演示凭据和无用导出组件；真正秘密移到服务端。
4. 在兼容前提下加入防调试、防篡改、完整性校验、签名校验、关键逻辑最小暴露和风险环境检测。
5. 当前环境有可信第三方加固工具且与目标 Android、ABI、JNI、模型和插件兼容时，实际执行第三方加固；不得为追求强度破坏正常功能。
6. 加固完成后使用该项目最终交付给用户的签名文件进行最终签名，不得使用用户无法取得的 AI 私有签名。
7. 签名校验、防篡改白名单和证书指纹必须对应同一份交付签名；用户使用该签名构建未来升级版本时应能正常通过校验。
8. 记录加固前后 APK 的 SHA-256、大小、包名、版本、签名证书指纹、加固方式和未验证项。

第三方加固若会改写 APK，必须按工具要求确定正确顺序，通常在加固后再使用项目签名进行最终签名；不得对最终签名后的 APK 再做会破坏签名的修改。

## 正式 App 要求

- 处理状态栏、刘海、挖孔、底部导航栏和手势安全区；正文不得顶到系统时间或压住手势条。
- 使用 Android 自适应图标，前景/背景分离并验证常见圆形、圆角方形和水滴蒙版。
- 权限按需申请，首次启动不得索取与核心功能无关的权限。
- 文件选择、保存、分享和备份使用系统兼容方式，处理不同品牌目录差异与分区存储。
- 列表、图片、OCR、音频、模型和大文件任务需控制内存、线程、电量和后台生命周期，支持暂停、取消、重试与异常恢复。
- 网络功能需处理超时、断网、重复提交、HTTP/HTTPS切换、服务端版本不兼容和登录失效。

## 构建、签名与加固验收

至少验证：干净构建、APK结构、对齐、最终签名、签名验证、直接安装、首次启动、使用同一签名的覆盖升级、核心流程、权限拒绝、断网、HTTP/HTTPS、低存储、长任务、JNI/模型、崩溃日志和加固后兼容。

最终交付至少包含：已签名可安装 APK、证书指纹、安装测试结果；新项目且用户无历史签名时，另含私密签名文件及凭据说明。不得只交未签名包。
