# Android App Skill

## 开发前安全确认

App 连接云端、账号系统、云控或后台时，只询问用户尚未说明的内容：部署范围、云端基础地址、是否使用 HTTPS、地址固定打包还是允许配置、认证方式、是否需要加强/第三方加固、是否已有正式签名证书。

云端基础 URL 本身通常不是秘密，即使拆分或混淆也可能从 APK 或网络流量中恢复。安全必须依靠 HTTPS、服务端鉴权、权限校验、短期令牌、重放防护和限速。可公开的 App Key 可以放入客户端；任何能直接授权敏感操作的 App Secret、管理员密码、数据库密码、签名私钥或长期万能令牌不得打包进 APK。

## 技术路线

### 未要求 AIDE/AIDE-Plus

根据产品需求、性能、设备覆盖、现有项目和维护成本，选择原生 Android、Flutter 或成熟可靠方案。不要为了迎合 AIDE 限制而牺牲正常工程质量。

默认交付要求：

- 必须实际生成可安装 APK。
- 默认不强制交付 Android 源码；用户明确要求源码时再交付。
- 不得只交工程目录、伪 APK、网页快捷方式或无法安装的占位文件。
- 实际执行构建并记录构建方式、最低 Android 版本、目标版本、包名、版本号和 APK 路径。

### 明确要求 AIDE/AIDE-Plus

- 优先原生 Android/Java、Groovy Gradle、少依赖和本地静态资源。
- 工程必须可在 AIDE-Plus 直接打开和编译，交付 APK 与完整 Android 源码。
- 复杂 Kotlin、JNI、ONNX、OpenCV、PaddleOCR 等产物应提前构建为兼容 AAR/JAR/so 或静态模型，再作为工程输入。
- 不得声称 AIDE 可编译却只在 Android Studio 验证。

## 默认发布安全

所有正式 release APK 默认执行，不需要用户额外要求：

- `debuggable=false`，移除测试入口、调试证书、演示账号和敏感日志。
- 启用适合当前构建链的代码压缩、资源压缩、优化和混淆，并保留反射、JNI、序列化和插件所需规则。
- 仅导出确有需要的 Activity、Service、Receiver、Provider，并为导出组件添加权限或输入校验。
- 默认禁止明文 HTTP；确需 HTTP 时限定域名和用途并说明风险。
- 访问令牌存入 Android Keystore 支持的安全存储，不把长期秘密写入 strings.xml、assets、BuildConfig 或本地明文数据库。
- 使用正式 release 证书签名；签名私钥和密码不得放入源码或交付包。
- 检查备份、截图、剪贴板、WebView、深链、文件 URI、日志和崩溃上报中的敏感信息。

## 用户要求“加固 APK”时

直接执行可用的加固、构建、签名和安装验证，不再只给方案。

### 内置加强加固

在默认发布安全基础上，根据兼容性加入必要的防调试、防篡改、完整性校验、关键字符串/协议最小暴露、签名校验和风险环境检测。任何措施都必须有正常设备兼容和误报测试，不得让安全逻辑导致无法启动、无法更新或错误封禁。

### 第三方壳加固

只有当前环境实际具备可信工具、用户允许使用且与目标 Android 版本、ABI、签名和插件兼容时才执行。完成后必须重新签名或按服务流程签名，并验证安装、升级、启动、网络、推送、文件、模型/JNI 和核心流程。

若第三方工具不可用，明确交付“已完成内置加强加固的 APK”，并把“第三方壳未执行”列为未验证/未完成项；不得把 R8 混淆冒充完整壳加固。

## 正式 App 要求

- 处理状态栏、刘海、挖孔、底部导航栏和手势安全区；正文不得顶到系统时间或压住手势条。
- 使用 Android 自适应图标，前景/背景分离并验证常见圆形、圆角方形和水滴蒙版。
- 权限按需申请，首次启动不得索取与核心功能无关的权限。
- 文件选择、保存、分享和备份使用系统兼容方式，处理不同品牌目录差异与分区存储。
- 列表、图片、OCR、音频、模型和大文件任务需控制内存、线程、电量和后台生命周期，支持暂停、取消、重试与异常恢复。
- 网络功能需处理超时、断网、重复提交、证书错误、服务端版本不兼容和登录失效。

## 构建与加固验收

至少验证：干净构建、签名、安装、首次启动、覆盖升级、核心流程、返回键/手势、配置变化、权限拒绝、断网、低存储、长任务、崩溃日志和加固后兼容。保留反混淆映射文件但不得公开；未能在真实设备安装或未执行第三方壳时必须准确标记。
