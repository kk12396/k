# 发布、迁移与交付 Skill

## 版本与文档

- 使用语义化版本或项目既有版本规则，压缩包、APK、EXE 和文档中的版本保持一致。
- 项目必须维护 `docs/FEATURES.md`、`docs/CHANGELOG.md`、`docs/DEV_PROGRESS.md`；Web 项目包含 `install.php`。
- 更新前读取 FEATURES，更新后只追加、补充或修正；废弃功能标记“已替换/已废弃”。
- CHANGELOG 记录新增、修改、修复、安全、数据库、表前缀、Android API、兼容性、加固、签名和升级操作。

## 数据库表前缀与迁移

- Web 安装器必须允许用户自定义数据库表前缀，并将最终值写入统一配置；所有模块、SQL、迁移、CLI、定时任务和备份恢复使用同一表名解析逻辑，禁止硬编码完整表名。
- 表前缀只允许字母、数字和下划线，并执行长度限制、冲突检查和安全标识符封装。
- `schema.sql` 使用前缀占位符或安全替换机制；迁移记录表也跟随当前前缀。
- 旧站升级必须读取并沿用原表前缀，不得恢复默认前缀、静默更换前缀或另建空表。
- 修改前缀必须作为独立迁移操作，先备份、检测目标冲突并提供回滚；不得在普通版本升级中自动改前缀。
- 每个迁移有唯一版本、幂等检测、事务边界、失败日志和安全重试策略。
- 已执行历史迁移不得随意改内容导致校验值变化；需修正时新增补丁迁移。
- 升级路径至少验证：全新安装默认前缀、自定义前缀、上一版本原前缀升级、重复执行、部分失败后重试和旧数据保留。
- Web 新增数据库功能同步更新实际后台路径下的迁移器、CLI 迁移、安装器和 `schema.sql`。

## Android API 发布基线

除非用户本次明确覆盖，所有 Android 产物固定采用：

- `minSdk=23`：最低支持 Android 6.0 / API 23。
- `targetSdk=36`：目标 Android 16 / API 36。
- `compileSdk=36`：编译 Android 16 / API 36。
- 不设置 `maxSdkVersion`：最高支持不设限制。

发布要求：

- 构建环境必须具备 Android SDK Platform 36 和兼容 AGP/Gradle/JDK 或 Flutter 工具链，不得静默降低 `targetSdk`、`compileSdk`。
- 必须检查源码 Manifest、依赖 Manifest 和最终合并 Manifest，确保没有 `maxSdkVersion`。
- 依赖、AAR、插件、JNI/so 和加固工具必须同时兼容 API23 与 API36，不得静默提高 `minSdk`。
- 目标 API36 的权限、后台、存储、通知、前台服务、安全和界面行为变化必须实际适配，不能只修改 Gradle 数字。
- “最高支持不设限制”不代表未来系统已经完成实测；新系统发布后仍需增量兼容验证。

## 构建产物

- Android：交付实际构建、已经签名并可直接安装使用的 APK；明确要求 AIDE 时另交 AIDE-Plus 可编译源码。
- App+网页双端：已签名可安装 APK + 可部署网页版源码。
- 网页+Android+PC 三端：已签名可安装 APK + Windows EXE + 可部署网页版源码。
- Android/PC 源码仅在用户明确要求，或明确要求 AIDE/AIDE-Plus 时按约定交付。
- 不得用未签名 APK、快捷方式、空壳、改后缀文件或未编译工程冒充正式产物。

## Android 签名管理

### 已有应用或旧项目

- 开始构建前要求用户提供原签名文件、别名和密码。
- 所有升级版本必须沿用原签名，否则无法正常覆盖安装，应用内签名校验也可能失败。
- 不得使用临时测试签名替换原签名后交付。

### 新项目且用户没有签名文件

- 为该项目生成独立 release 签名文件，不得跨用户或跨项目复用。
- 使用该签名完成最终 APK 签名，保证 APK 可直接安装。
- 随私密交付包一并提供签名文件、别名、密码、证书 SHA-256 指纹、有效期和备份说明。
- 签名文件及密码不得上传公开 GitHub、放进公开源码包或写入日志。
- 提醒用户长期备份；未来更新必须继续使用同一签名。

## Android 加固

所有正式 APK 默认执行 release 安全检查。用户明确说“加固 APK”时，不再询问加固等级，直接执行当前环境、构建链和项目兼容范围内能做到的最好加固，允许使用可信第三方工具。

至少执行：

1. 生成加固前 release APK，记录 SHA-256、大小、包名和版本。
2. 关闭调试和测试配置，移除敏感日志、测试接口、演示账号与秘密字符串。
3. 执行代码/资源压缩、优化和混淆，补齐反射、JNI、序列化、路由、模型与插件保留规则。
4. 收敛导出组件，检查 WebView、深链、备份、剪贴板、本地存储和 HTTP 放行范围。
5. 在兼容前提下加入防调试、防篡改、完整性/签名校验、关键逻辑最小暴露和风险环境检测。
6. 当前环境有可信且兼容 API23/API36 的第三方加固工具时实际执行；否则交付最高可实现的内置加固并准确说明。
7. 加固结束后，使用该项目最终交付给用户的签名文件完成最终签名和对齐。
8. 应用内签名校验和防篡改证书白名单必须对应同一份交付签名，不能绑定用户拿不到的签名。
9. 检查最终 APK 的 `minSdk=23`、`targetSdk=36`，确认合并 Manifest 不含 `maxSdkVersion`。
10. 记录加固后 APK 的 SHA-256、大小、版本、签名指纹、加固方式和兼容测试结果。

若第三方工具会改写 APK，应在其完成后再使用项目签名进行最终签名；最终签名完成后不得继续修改 APK 内容。

## 网页发布检查

- 新版固定 PHP8.2 + MySQL8.0；旧版固定 PHP7.4 + MySQL5.6/5.7，并检查安卓手机 KSWEB 兼容。
- 后台自用版固定 `/adminsc + admincs/asd.cc`；经典版固定 `/admin + admin/123456`。
- 不强制首次登录改密；登录页不得展示凭据，数据库只保存密码哈希。
- 默认兼容 HTTP 与 HTTPS，不强制证书；使用 HTTP 时检查 Cookie、回调、资源和 API 不因 Secure 或硬编码 HTTPS 失效。
- `install.php` 必须显示可编辑的数据库表前缀，并验证默认前缀、自定义前缀、空前缀兼容及同数据库多实例隔离。
- 全站不得存在绕过统一表名解析器的硬编码物理表名；升级、备份恢复和 CLI 必须继续使用安装时选定的前缀。

## 云控发布检查

只有功能确实需要云控时才检查并接入用户提供的云控地址与资料。不得为普通本地软件强行增加云控，也不得把 App Secret、管理员密码、数据库密码或长期万能令牌打包进客户端。

## 发布前检查

1. 语法、依赖、路径和配置模板。
2. 干净环境构建及产物存在性。
3. Android `minSdk=23`、`targetSdk=36`、`compileSdk=36`，最终合并 Manifest 无 `maxSdkVersion`。
4. APK 加固、对齐、最终签名、签名验证、直接安装、API23/API36运行、同签名覆盖升级；EXE 启动；Web 安装/部署。
5. 新项目签名文件是否已在私密交付包中提供，且未进入公开仓库。
6. 数据库默认前缀、自定义前缀、旧站原前缀、迁移重复执行、备份恢复和旧数据。
7. 登录、权限、上传下载、离线、重试和异常恢复。
8. 客户端秘密、后台凭据、安全、隐私和日志泄露。
9. HTTP/HTTPS、本地/KSWEB、云控可选接入和地址异常。
10. UI、安全区、图标、响应式和正式文案。
11. 功能矩阵与 FEATURES 对照，确认旧功能未丢失。
