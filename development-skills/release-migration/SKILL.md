# 发布、迁移与交付 Skill

## 版本与文档

- 使用语义化版本或项目既有版本规则，压缩包、APK、EXE 和文档中的版本保持一致。
- 项目必须维护 `docs/FEATURES.md`、`docs/CHANGELOG.md`、`docs/DEV_PROGRESS.md`；Web 项目包含 `install.php`。
- 更新前读取 FEATURES，更新后只追加、补充或修正；废弃功能标记“已替换/已废弃”。
- CHANGELOG 记录新增、修改、修复、安全、数据库、兼容性、加固和升级操作。

## 数据库迁移

- 每个迁移有唯一版本、幂等检测、事务边界、失败日志和安全重试策略。
- 已执行历史迁移不得随意改内容导致校验值变化；需修正时新增补丁迁移。
- 升级路径至少验证：全新安装、上一版本升级、重复执行、部分失败后重试和旧数据保留。
- Web 新增数据库功能同步更新后台迁移器、CLI 迁移、安装器和 `schema.sql`。

## 构建产物

- Android：交付实际构建并签名的 APK；明确要求 AIDE 时另交 AIDE-Plus 可编译源码。
- App+网页双端：APK + 可部署网页版源码。
- 网页+Android+PC 三端：APK + Windows EXE + 可部署网页版源码。
- Android/PC 源码仅在用户明确要求，或明确要求 AIDE/AIDE-Plus 时按约定交付。
- 不得用快捷方式、空壳、改后缀文件或未编译工程冒充 APK/EXE。

## Android 发布安全与加固

所有正式 APK 默认检查：release 构建、关闭调试、移除敏感日志和测试入口、代码/资源优化与混淆、最小导出组件、正式签名、明文流量限制、客户端秘密扫描和安装升级。

用户明确要求“加固 APK”时，必须直接执行当前环境可完成的加固流程，而不是只提供方案：

1. 生成加固前 release APK 并记录 SHA-256、包名、版本和签名。
2. 执行内置加强加固并保留必要映射/符号文件。
3. 若存在用户指定或已获许可的可信第三方工具，执行壳加固并按正确顺序签名。
4. 对加固后 APK 再次记录 SHA-256、签名、大小和版本。
5. 实际验证安装、覆盖升级、首次启动、网络、推送、文件、JNI/模型、登录和核心流程。
6. 明确区分“默认发布安全”“内置加强加固”“第三方壳加固”的完成状态。

第三方壳工具不可用、签名证书缺失或兼容测试失败时，不得声称完整加固；应交付可用的内置加固 APK，并记录未执行原因和风险。

## 后台与默认凭据发布检查

- 确认实际后台路径和初始管理员方案与用户选择一致。
- 登录页和公开文档不得展示默认账号密码。
- 本机/内网/测试可按用户要求使用弱初始密码；公网发布必须自定义强密码或生成随机密码并首次登录强制改密。
- 检查登录限速、会话安全、CSRF、对象级权限、失败日志和默认账号是否已修改。

## 发布前检查

1. 语法、依赖、路径和配置模板。
2. 干净环境构建及产物存在性。
3. APK 签名/加固/安装/升级、EXE 启动、Web 安装/部署。
4. 数据库迁移与旧数据。
5. 登录、权限、上传下载、离线、重试和异常恢复。
6. 客户端秘密、后台默认密码、安全、隐私和日志泄露。
7. UI、安全区、图标、响应式和正式文案。
8. 功能矩阵与 FEATURES 对照，确认旧功能未丢失。

## 最终报告

列出版本号、产物、检查范围、修复项、数据库变化、后台路径与凭据安全状态、APK签名/加固层级、测试结果、未验证项、已知限制和升级步骤。只有在实际生成并检查产物后才能提供“已完成”结论。
